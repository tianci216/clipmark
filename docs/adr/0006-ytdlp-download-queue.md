# In-memory sequential Download queue behind an injected `Downloader`

Getting an online video into the library meant a terminal and yt-dlp by hand. We decided the server runs yt-dlp itself: `POST /api/downloads` enqueues a Download (URL plus an existing subfolder of the Library Folder), a **single in-memory queue** runs Downloads **one at a time in order**, `GET /api/downloads` is polled by the client (~1s while anything is in flight), and `DELETE /api/downloads/:id` cancels a running Download (SIGINT), drops a queued one, or dismisses a finished row. Nothing is persisted: a restart forgets the queue, and a landed file is simply a Video the scanner finds on the next `/api/tree`.

The process sits behind one interface, `Downloader` (`start(request, events) → { cancel }`, `testCookies(browser)`, `status()`), injected into `createApp`. Production (`server/src/ytdlp.ts`) spawns yt-dlp with `--no-playlist`, an avc1+mp4a format chain forced into mp4 (`--recode-video mp4` as the fallback — accepted gap: a site offering only VP9/AV1 *inside* an mp4 container and no avc1 at all lands un-transcoded, since yt-dlp skips recoding when the container already matches), the output template `<folder>/%(title)s [%(id)s].%(ext)s`, and `--print before_dl:title` / `--print after_move:filepath` so the queue learns the title and the landed path from stdout instead of guessing filenames. The HTTP suite (`test/app.test.ts`) drives the queue with a scripted fake and no yt-dlp, which is where order, progress, cancel cleanup and failure are covered.

Partial-file cleanup does not try to predict yt-dlp's names: the queue snapshots the destination's `*.part` / `*.ytdl` files before a Download starts and removes only the ones that appeared since. This is safe because at most one runs at a time.

Cookies: yt-dlp reads the browser's cookie store (`--cookies-from-browser`, default `chrome`, stored in the `settings` table as `cookies_from_browser`; `none` omits the flag). Reading Chrome's store triggers a one-time macOS Keychain prompt aimed at the server process, so `POST /api/downloads/test-cookies` runs yt-dlp in simulate mode against a fixed public URL to surface that prompt on demand. yt-dlp is resolved from the same directories the macOS shell uses for node (`/opt/homebrew/bin`, `/usr/local/bin`, `/usr/bin`) — not bundled, not auto-updated; `GET /api/settings` reports its path and version or `null` — the one absolute path the API exposes (ADR-0005 keeps video paths folder-relative; a binary's location is not a library path). Amends ADR-0005: the settings response and `PUT /api/settings` grow `cookiesFromBrowser` and `ytDlp`.

Rejected: persisting Downloads in SQLite (a Download is transient by definition — CONTEXT.md — and its outcome is the file), concurrent downloads (bandwidth and disk contention for no user benefit), and a folder browser or native picker (the picker lists the subfolders `/api/tree` already knows).
